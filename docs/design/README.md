# 디자인 가이드

코드 대조일: 2026-10-30

이 가이드는 기존 UI의 의도와 재사용 기준을 AI와 사람이 찾을 수 있도록 정리합니다. [문서 위계](../README.md)에 따라 서비스·기능 설계를 연결하고, 실제 토큰 값과 컴포넌트 API는 코드에서 확인합니다. 이번 작성은 정적 대조이며 화면·접근성·모든 테스트를 새로 검증한 기록은 아닙니다.

## UI 작업에서 읽는 순서

1. 요청의 사용자·행동·바뀔 상태·제약을 확인합니다. 빠진 의도는 가정으로 밝히고, 권한·데이터·제출 방식까지 달라질 해석은 구현 전에 확인합니다.
2. 아래 표에서 대상 영역을 고릅니다. 같은 서비스라도 관리자와 공개 테마의 시각 표현을 하나로 통일하지 않습니다.
3. [토큰과 컴포넌트](foundations.md)에서 해당 영역의 재사용 대상을 찾습니다.
4. 입력 작업은 [폼 패턴](patterns/form.md), 로딩·결과·빈 상태·확인은 [피드백 패턴](patterns/feedback.md), 선물 카드는 [위시 카드 패턴](patterns/wish-card.md)을 읽습니다. 관련 없는 과거 계획 전체를 문맥에 넣을 필요는 없습니다.
5. 아래 화면 참조와 코드를 대조하고, 유지할 계약·미결정 사항·확인 방법을 작업 범위에 맞게 정합니다.

## 디자인 영역

| 영역 | 의도와 현재 표현 | 우선 확인할 구현 |
| --- | --- | --- |
| 홈·로그인·온보딩 | 서비스 소개와 생성 진입. 고정 픽셀 브랜드 표현을 사용하며 사용자의 선택 공개 테마는 적용하지 않음 | [홈](../../app/page.tsx), [로그인](../../app/login/page.tsx), [온보딩](../../app/onboarding/page.tsx) |
| 관리자 상시 작업 | 반복 입력과 상태 확인을 위한 차분한 레이아웃. 목록·폼·버튼 위계를 우선 | [관리자 shell](../../app/admin/layout.tsx), [관리자 UI](../../app/admin/admin-ui.tsx) |
| 공개 위시리스트·샘플 | 생일 카드처럼 가볍게 공유. 세 테마가 같은 정보 구조·행동을 공유 | [공개 뷰](../../components/public-wishlist-view.tsx), [샘플](../../app/sample/page.tsx) |
| 관리자 첫 진입 안내 | 차분한 shell 안의 명시적 브랜드 강조 예외. 모달과 비네트에 굵은 선·그림자·테마 미리보기 사용 | [기능 설계](../superpowers/specs/2026-07-22-admin-first-entry-guide-design.md), [Dialog](../../app/admin/admin-guide-dialog.tsx), [비네트](../../app/admin/admin-guide-visual.tsx) |

기본 방향은 [Public Pixel / Admin Calm](../superpowers/specs/2026-05-14-mwagotgo-sipeo-visual-system-design.md)입니다. Public Pixel은 기본 브랜드 인상이지 모든 공개 테마를 픽셀로 만들라는 뜻이 아닙니다. Core UI도 모든 화면에서 브랜드 표현을 제거하라는 뜻이 아닙니다.

## 유지할 원칙과 근거

- 공개 테마가 달라져도 선물·진행률·참여·계좌 안내의 정보 구조와 도메인 규칙은 공유합니다. 근거: [서비스 설계](../superpowers/specs/2026-05-14-mwagotgo-sipeo-service-design.md#131-디자인-시스템-원칙), [공통 공개 뷰](../../components/public-wishlist-view.tsx).
- 테마의 시각적 차이는 토큰과 기존 표현으로 유지합니다. 관리자 화면에 선택 공개 테마를 전역으로 적용하지 않습니다. 근거: [테마 CSS](../../app/public-themes.css), [관리자 shell](../../app/admin/layout.tsx).
- 기존 컴포넌트·필드·제출 경로를 먼저 확인합니다. 모양이 비슷하다는 이유만으로 모든 폼을 하나의 컴포넌트나 새 라이브러리로 바꾸지 않습니다. 근거: [재사용 지도](foundations.md), [폼 패턴](patterns/form.md).
- 공개 카피는 짧고 친근하게 쓰되 금액 기록과 실제 결제·송금을 혼동시키지 않습니다. 근거: [카피 원칙](../superpowers/specs/2026-05-14-mwagotgo-sipeo-visual-system-design.md#copy-tone), [참여 안내 문구](../../src/lib/design/copy.ts), [참여 저장](../../src/lib/public-participation/repository.ts).
- 키보드 포커스·레이블·오류와 대기 상태는 별도 확인 대상입니다. 기존 스타일 재사용만으로 접근성이 보장된다고 판단하지 않습니다. 근거: [공통 Button](../../components/ui/button.tsx), [관리자 안내 접근성 설계](../superpowers/specs/2026-07-22-admin-first-entry-guide-design.md#11-접근성), [공개 필드 스타일](../../app/public-themes.css).

## 화면 참조

외부 제품의 스타일을 새로 가져오기 전에 같은 영역의 실제 화면과 사용 이유를 확인합니다. 아래는 코드 참조 목록이며, 이번 작업에서 캡처·시각 승인한 스크린샷 목록은 아닙니다.

| 작업 | 기준 화면·코드 | 참고할 판단 |
| --- | --- | --- |
| 공개 테마 비교 | `/sample?theme=pixel_y2k`, `mono_bw`, `soft_pastel` / [샘플](../../app/sample/page.tsx) | 같은 콘텐츠를 테마별로 표현. 데모는 저장하지 않음 |
| 선물 입력·목록 | `/admin/wishes` / [화면](../../app/admin/wishes/page.tsx) | 접힌 추가 영역, 필드 재사용, 첫 0건과 필터 0건의 행동 구분 |
| 관리자 결과 안내 | [토스트 이벤트](../../app/admin/admin-toast-events.tsx), [온보딩](../../app/onboarding/page.tsx) | 결과 토스트와 페이지 내 오류가 현재 다르게 사용됨 |
| 로딩·실패·빈 상태 | [피드백 패턴](patterns/feedback.md) | 전체 페이지 실패와 일부 작업 실패를 구분 |
| 안내 모달·모션 | [관리자 첫 진입 안내 설계](../superpowers/specs/2026-07-22-admin-first-entry-guide-design.md) | 해당 기능의 단계·닫기·포커스·reduced-motion 기준 |

새 레퍼런스를 추가할 때는 화면 위치·어떤 문제를 풀었는지·적용 영역·확인 날짜를 함께 기록합니다. 외부 사례를 제품의 합의된 규칙으로 바로 격상하지 않습니다.

## 패턴을 기록하는 방법

| 구분 | 기록할 내용 |
| --- | --- |
| 현재 구현 | 코드 대조일·실제 동작·근거 파일. 구현이 있다는 사실과 검증 결과를 구별 |
| 유지할 규칙 | 적용 상황·재사용 대상·보존할 흐름과 이유 |
| 차이와 미결정 | 일관되지 않은 상태·미구현 의도·확인하지 않은 품질. 새 기능의 완료 조건으로 묵시적으로 바꾸지 않음 |
| 확인 방법 | 관련 테스트와 화면에서 확인할 상태. 테스트의 존재와 실행 통과를 구별 |

예를 들어 공개 참여에는 pending 처리가 있지만 관리자 선물 등록에는 같은 처리가 없습니다. 이 차이는 [폼 패턴](patterns/form.md)에 남기고, ‘모든 폼이 이미 중복 제출을 막는다’고 설명하지 않습니다.

## 문서 사용 효과 확인

첫 적용 사례는 기존 [관리자 선물 추가 폼](../../app/admin/wishes/page.tsx)처럼 범위가 작은 UI 작업으로 잡을 수 있습니다. 동일한 요청·코드 시작점·확인 조건을 유지해 가이드 참조 전후 결과를 비교합니다. 이번 문서 작업에서 비교 실험을 수행한 것은 아닙니다.

- 기존 토큰·컴포넌트·제출 경로를 재사용했는지 확인합니다.
- 요청에 필요한 초기·검증 실패·제출 중·성공·실패 상태를 검토하고, 없는 상태를 처리했다고 주장하지 않습니다.
- 사람이 수정한 부분과 이유를 기록해 실제로 판단 부담이 줄었는지 확인합니다.
- UI를 변경한 경우 기존 검증에 더해 대상 화면·테마·반응형·키보드 동작을 확인합니다. [기존 E2E 범위](../../specs/README.md)는 시각적 회귀나 전체 접근성 검증과 구분합니다.

새 라이브러리, Storybook, 디자인 DSL이나 문서 검색 도구의 도입은 이 가이드의 선행 조건으로 두지 않습니다. 현재 재사용 대상과 패턴을 먼저 연결하고, 필요가 확인되는 별도 작업에서 결정합니다.
